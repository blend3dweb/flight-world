## 14. Agent Bridge — присутствие нейромодели внутри виртуального мира

Статус: начат, работает прототип 0.3.0 с активным многопозиционным наблюдателем и управляемым полётом. Назначение этапа — дать нейромодели возможность непосредственно наблюдать работающую WebGPU-сцену, перемещаться в ней, исследовать дефекты и проверять внесённые изменения без экспорта видео и обязательного сохранения рендеров в файлы. Текущий протокол: [AGENT_BRIDGE_PROTOCOL.md](AGENT_BRIDGE_PROTOCOL.md).

### Архитектурный принцип

Agent Bridge связывает живую симуляцию и нейромодель двусторонним локальным каналом. Сцена передаёт визуальные и структурированные наблюдения прямо из текущего состояния приложения, а агент возвращает ограниченный набор команд управления. Видеофайл для этого контура не создаётся. Визуальный сигнал читается из framebuffer в памяти только с нужной частотой и разрешением.

Контур работы:

`сцена → наблюдение → анализ нейромоделью → действие → новое состояние сцены → повторная проверка`.

### Границы первого прототипа

- Agent Bridge работает только локально и не публикует управляющий интерфейс во внешний интернет.
- Первый прототип управляет наблюдателем и состояниями сцены, но не изменяет исходный код без отдельного рабочего цикла разработки.
- Непрерывное изображение не требуется: агент получает кадр по событию, при движении или для подтверждения результата.
- Пользовательские камеры, управление самолётом и обычный режим демонстрации продолжают работать независимо от агента.

## 15. Разделение геометрии и Gaussian-слоя: чек-лист оптимизации

Статус: пункт 15.1 выполнен, слои 15.2–15.5 ещё не реализованы. Источник: [техническая записка](../tmp2/Gaussian_Splatting_technical_note.pdf), разделы 1–5, 8–10. Целевая схема: `точная геометрия/семантика → источник формы и данных; Gaussian → внешний вид статичных деталей`. Записка описывает реконструкцию снятых объектов, поэтому для процедурной Океании отдельно проверяем источник визуальных данных и реальный выигрыш. Наличие Gaussian-слоя само по себе не гарантирует ускорения. [Отчёт базового замера](STAGE_15_1_BASELINE.md).

### 15.1. База и границы пробы

- [x] Зафиксировать маршрут через квартал ID 12, ракурс и условия: **10:00, сухая погода, без циклов**, постоянная экспозиция; это тестовый режим, функции смены суток и погоды в приложении сохранены.
- [x] Вывести FPS и время кадра в живой сцене, собирать покадровую историю в памяти; проверить паузу и продолжение без записи видео/снимков.
- [x] Измерить исходный FPS, медиану/p95 кадра, CPU-вызовы, GPU timestamps по проходам, draw calls, объём ресурсов и стоимость RGB-наблюдения агента. Память GPU измерена лишь для всего адаптера, а не точно для одного процесса; первый проход компиляции отделён от сравнения.
- [x] Выбрать статичный квартал ID 12 с четырьмя разными зданиями. Самолёт, океан, дороги, аэропорт и динамика не входят в Gaussian-пробу.
- [x] Проверить входные данные: калиброванных видов, сканов, depth/LiDAR и готовых Gaussian-ассетов в проекте нет; прежние кадры видео не дают новых деталей текущим домам.

### 15.2. Слой точной геометрии (geometry truth)

- [ ] Сохранить координаты, размеры, уровни земли, силуэты зданий и проёмы в mesh; при необходимости исследовать SDF/поверхностное представление только для конкретных сложных форм, а не вводить его повсеместно.
- [ ] Задать структурные ограничения выбранного квартала: плоскости фасадов/крыш, углы, окна, входы и уровни этажей; проверить, что визуальный слой не искажает их положение.
- [ ] Оставить на геометрии коллизии, raycast, depth/normal/object-ID, семантику и привязку к модулю кода для Agent Bridge. Gaussian-примитивы не становятся источником точных размеров или идентификаторов.
- [ ] Если будут реальные исходные виды, привязать камеры и depth/облако точек к той же системе координат, что и mesh; проверить масштаб и совмещение до обучения визуального слоя.

### 15.3. Gaussian-слой внешнего вида (appearance)

- [ ] Сделать переключатель «исходный квартал / geometry truth + Gaussian» для одинакового маршрута и мгновенного отката.
- [ ] На одном квартале сравнить поверхностные 2DGS/surfels или Gaussian, привязанные к mesh, с обычными объёмными 3DGS; выбрать вариант с наименьшими «плавающими» деталями и приемлемой стоимостью рендера.
- [ ] При обучении/подготовке использовать RGB вместе с доступными depth и normals для привязки к поверхности; если точных источников нет, не заявлять метрическую точность результата.
- [ ] Предусмотреть multi-scale/LOD и антиалиасинг для дальнего и близкого вида; ограничить число видимых примитивов, экранное перекрытие, размер ресурсов и загрузку только нужного сектора.
- [ ] Встроить выбранный визуальный слой в существующий WebGPU-рендер с корректной глубиной относительно mesh, без второго постоянно работающего рендерера; проверить прозрачность, сортировку, мерцание и поворот камеры.
- [ ] Сохранить Agent Bridge доступ к прямому RGB-наблюдению из памяти и к геометрическому слою; не создавать видео или файлы снимков для нейромодели.

### 15.4. Сравнение и решение

- [ ] На зафиксированном тестовом маршруте сравнить исходный квартал и гибрид: читаемость архитектуры, стабильность изображения, медиану/p95 времени кадра, паузы, память и объём загрузки.
- [ ] Принять расширение только при видимом улучшении деталей **и** снижении p95 времени кадра на целевом маршруте без ухудшения пауз/памяти сверх заранее зафиксированного бюджета. Если ограничение связано с океаном, тенями или вторым сеансом агента, оптимизировать их отдельно.
- [ ] Зафиксировать решение «расширять / доработать / отказаться» и ограничения по исходным данным. Не переводить весь город на Gaussian до результата пробы.

### 15.5. Позднее возвращение динамических условий

- [ ] После успешной статичной пробы отдельно исследовать relighting/PBR-параметры Gaussian-слоя (albedo, normal, roughness) или другие способы согласовать его с солнцем и ночным освещением; оценить цену дополнительных проходов.
- [ ] Затем вернуть день/ночь, дождь, снег, тени и отражение в океане по одному и проверить каждое условие на том же маршруте. До этого тестовый режим остаётся с фиксированными днём и сухой погодой.

Демонстрационные рендеры и видео не создаём до отдельной команды. Вывод о качестве и скорости делаем по живой сцене, прямому наблюдению агента и численным измерениям.
